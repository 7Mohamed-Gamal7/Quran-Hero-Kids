# قرارات التصميم

## ADR-001: حساب ولي الأمر هو هوية الدخول في MVP

**الحالة:** مقترح معتمد للتأسيس
**القرار:** حساب واحد لولي الأمر وملفات أطفال تابعة له؛ لا حساب مستقل للطفل في MVP.
**السبب:** تقليل جمع بيانات الطفل وتبسيط الإشراف والتفويض.
**الأثر:** كل بيانات الطفل محكومة بملكية الأسرة؛ يمكن إعادة تقييم حساب الطفل المستقل بعد مراجعة الخصوصية وسيناريوهات الاستخدام.

## ADR-002: أحادية تطبيق/واجهة API كبداية

**الحالة:** مقترح معتمد للتأسيس
**القرار:** Flutter واحد بنمط ملف ولي الأمر/الطفل، وخدمة ASP.NET Core منظمة بطبقات داخلية بدل microservices.
**السبب:** سرعة التحقق من MVP وتقليل التعقيد التشغيلي.
**الأثر:** فصل حدود الوحدات جيدًا حتى يمكن استخراج خدمات عند وجود بيانات حمل فعلية.

## ADR-003: تأجيل تحليل التلاوة والصوت

**الحالة:** معتمد ضمن MVP
**القرار:** لا رفع لتسجيلات الطفل ولا تقييم صوتي آلي في الإصدار الأول.
**السبب:** حساسية بيانات الطفل، صعوبة ضمان الدقة في اللهجات والضوضاء، والحاجة إلى موافقات واحتفاظ واضحين.
**الأثر:** يقتصر MVP على الاستماع والتكرار والاختبارات النصية؛ تقيم الميزة مستقبلًا على بيانات اختبار مناسبة وموافقة صريحة.

## ADR-004: مصدر المحتوى قبل بناء قاعدة القرآن

**الحالة:** مفتوح حتى اختيار المصدر
**القرار:** لا تعبئة إنتاجية لنصوص/تلاوات قبل توثيق المصدر والترخيص وآلية checksum.
**السبب:** سلامة النص والحقوق شرط أساسي.
**الأثر:** مخطط البيانات يظل محايدًا للمورد حتى اعتماد المصدر.
